# L&J Spa 2 Go Home

Real-time operations platform for a home-service massage business: booking,
a travel-aware scheduling engine, live therapist dispatch, a therapist
mobile PWA, a public client booking portal, and sales/expenses/performance
reporting — backed by real PostgreSQL data, real authentication, and real
authorization throughout. Nothing in this repo is a static mock; every
number on every page comes from a live query.

## Project overview

L&J Spa 2 Go Home is a 15-year-old home-service massage business. Therapists
travel to clients rather than clients visiting a location, which makes
*travel time* a first-class scheduling input, not an afterthought — a
therapist finishing one job at 3:30 PM with a 30-minute drive and a 10-minute
buffer is not available at 3:35, they're available at 4:10. The whole point
of this app is that the system enforces that math everywhere: the client
booking site, the dispatcher's "assign a therapist" screen, and the
commit-time check that runs again right before a booking is actually saved.

## Architecture

```
prisma/schema.prisma     Full domain schema (see "Database design" below)
prisma/seed.ts            Realistic dev seed data
src/proxy.ts               Next.js 16 route middleware (auth + page-level RBAC)
src/lib/
  auth/                       Session (JWT/httpOnly cookie), password hashing,
                                    the RBAC permission matrix, requireSession/requirePermission
  scheduling/               The scheduling engine (see below)
  travel/                      Travel-time provider abstraction (Google Distance Matrix
                                    or a Haversine-distance dev fallback)
  notifications/           SMS/Email provider abstraction (console fallback)
  payments/                  Payment provider abstraction (manual/cash by default)
  booking/                    Booking creation, the booking status state machine,
                                    commission calculation
  therapist-status/       The therapist live-status state machine
  dashboard/                Command Center KPI + live-board aggregation
  performance.ts             Per-therapist metrics (deliberately not one opaque score)
  system-user.ts             Attribution for bookings created by the public website
src/app/
  (staff)/                     Authenticated admin/dispatcher/accounting app
                                    (dashboard, bookings, calendar, live-map, therapists,
                                    clients, services, sales, expenses, performance,
                                    reports, notifications, settings, audit-log)
  (therapist)/app/       The therapist mobile PWA
  book/                          Public client booking portal (no auth)
  api/                            Every route re-checks authorization itself — see Security
```

### Why Next.js 16's `src/proxy.ts` instead of `middleware.ts`

Next.js 16 renamed the middleware convention to `proxy.ts`/`export async
function proxy()`. `next dev`/`next build` auto-generate an `AGENTS.md`
block pointing at `node_modules/next/dist/docs/` for exactly this kind of
version-specific detail — genuinely generated by Next, not a stray file;
worth knowing about if you see it and haven't run `next dev` before.

### Why the coarse `proxy.ts` gate doesn't cover `/api/*`

Early in development, `proxy.ts` gated `/api/services` and
`/api/therapists/me/schedule` to the same roles as their admin pages —
which incorrectly 403'd a dispatcher reading the service catalog to build a
booking, and a therapist reading their own schedule. Both were caught by
live testing (logging in as each role and hitting the actual endpoint), not
by `tsc`. The fix: `proxy.ts` now only gates *pages* (redirect-away UX).
Every API route independently calls `requireSession()` /
`requirePermission()` / an explicit "is this the resource owner" check
before touching Prisma — that is the real security boundary, and a mistake
in `proxy.ts` can no longer leak or block data. See the comment at the top
of `src/proxy.ts`.

## Tech stack

- **Framework:** Next.js 16 (App Router, Turbopack) + TypeScript, full-stack
- **Styling:** Tailwind CSS v4, custom design tokens (`src/app/globals.css`)
  — burgundy/black/off-white per the brand direction, dark "ops" theme for
  admin/dispatcher/therapist surfaces, warm off-white for the public site
- **Database:** PostgreSQL + Prisma ORM
- **Auth:** JWT session in an httpOnly cookie (`jose` + `bcryptjs`), RBAC
  enforced server-side (see [Security](#security))
- **Maps/travel:** Google Distance Matrix when `GOOGLE_MAPS_API_KEY` is
  configured, otherwise a Haversine-distance + average-speed estimator
  clearly flagged `isEstimate: true`. The Live Map uses Leaflet +
  OpenStreetMap tiles, which need no API key at all.
- **Testing:** Vitest — 29 unit tests covering the scheduling engine, the
  booking/therapist state machines, the commission calculator, the RBAC
  matrix, and GPS-privacy guarantees
- **Icons:** lucide-react · **Charts:** recharts (installed, not yet wired
  into a chart — see "What's next")

**this destroys all data in the target database** and is meant for local
development only; it is intentionally not run automatically by anything in
this repo.

## Testing

```bash
npm test           # run once
npm run test:watch
```

29 tests across 4 files:

- `tests/slot-math.test.ts` — the pure gap-fitting arithmetic at the core
  of the scheduling engine, including the spec's two critical scenarios
  verbatim (a 90-minute service + 30-minute travel + 10-minute buffer
  computes the correct next-available time; a schedule where travel would
  blow past a fixed next booking is rejected).
- `tests/commission-and-transitions.test.ts` — commission math (flat,
  percentage, therapist-specific override) and both state machines
  (booking and therapist status), including that a completed booking can
  never be transitioned away from (financial records are immutable).
- `tests/permissions.test.ts` — the RBAC matrix: a client has zero staff
  permissions, a therapist can only read their own bookings, accounting
  can see financial data but never therapist GPS, only super-admin/owner
  can manage users or read the audit log.
- `tests/public-availability-privacy.test.ts` — asserts the public-facing
  availability response can never contain a therapist's coordinates,
  under every code path (available now, available later, unavailable).

These are true unit tests — no database required, `server-only` is stubbed
in `vitest.config.ts`. Beyond the automated suite, the scheduling engine,
booking lifecycle, RBAC boundaries, and GPS-privacy guarantees were also
manually verified end-to-end against a live PostgreSQL instance during
development (see commit messages for the specific `curl` scenarios run —
double-booking rejection, working-hours-boundary rejection, the full
ASSIGNED → TRAVELING → ARRIVED → IN_SERVICE → COMPLETED lifecycle with
real commission creation, and a grep of the actual public API response
confirming no coordinate field is present).

## Deployment

This app needs (a) a persistent PostgreSQL database and (b) a Node.js host
that can run `next build`/`next start` — **Railway** is a good fit
(bundles Postgres + app hosting together, "deploy from GitHub" flow):

1. Sign up at [railway.app](https://railway.app), **New Project → Deploy
   from GitHub repo**, pick this repo.
2. **Add PostgreSQL**: `+ New → Database → Add PostgreSQL`, then set the
   app service's `DATABASE_URL = ${{Postgres.DATABASE_URL}}`.
3. **Set env vars** on the app service: `JWT_SECRET` (e.g. `openssl rand
   -hex 32`), `NEXT_PUBLIC_APP_NAME`, and `APP_URL` (the public domain
   from step 5 below — without this, links the app builds itself resolve
   to Railway's *internal* address behind the proxy). Add
   `GOOGLE_MAPS_API_KEY`/`MAPS_PROVIDER=google` and the SMS/email/payment
   vars only once you actually have those accounts — the app works
   correctly without them, just with the documented fallbacks.
4. **Deploy.** Railway runs `npm install` (which runs `prisma generate`
   via `postinstall`), `npm run build`, then `npm run start`.
5. **Get a domain**: Settings → Networking → Generate Domain. Then go back
   and set `APP_URL` to that domain (step 3).
6. **Initialize the database** once, from the app service's Console tab
   (or locally with `DATABASE_URL` pointed at the Railway database):
   ```bash
   npm run db:push
   npm run db:seed   # optional — only for a demo/staging environment
   ```

Every subsequent `git push` to the connected branch auto-redeploys.

## Roles (RBAC)

| Role | Can see financials | Can see GPS | Notable restrictions |
|---|:---:|:---:|---|
| SUPER_ADMIN | ✅ | ✅ | none |
| OWNER | ✅ | ✅ | none |
| MANAGER | – | ✅ | no user management, no audit log |
| DISPATCHER | – | ✅ | no financial data, no service management |
| ACCOUNTING | ✅ | – | no therapist GPS, no scheduling/assignment |
| THERAPIST | own earnings only | own location only | only their own bookings |
| CLIENT | own bookings only | never (see [GPS privacy](#gps-privacy)) | only their own data |

The full matrix lives in `src/lib/auth/permissions.ts` as a single
`Record<Role, Permission[]>` — the one source of truth the sidebar nav,
every API route, and the unit tests in `tests/permissions.test.ts` all
read from. Enforcement happens in the route handler (`requirePermission()`
or an explicit `isSelf` check), never just by hiding a sidebar link.

## The scheduling engine

The core formula (spec-mandated):

```
nextAvailable = max(end of current appointment, travel arrival time,
                     therapist working hours start) + required buffer
```

Implementation is split into two layers so the arithmetic is testable
without a database or a network call to a maps API:

- **`src/lib/scheduling/slot-math.ts`** — pure functions operating on plain
  minute integers: `earliestReadyTime`, `canReachInTime`,
  `fitServiceInGap`. No I/O. This is what `tests/slot-math.test.ts` tests
  directly, including the spec's two critical worked examples verbatim.
- **`src/lib/scheduling/availability-engine.ts`** — the orchestration
  layer. For a given therapist/date/service/destination, it walks the
  therapist's working windows (split around their lunch/rest break),
  their existing bookings for that day in order, and calls the travel
  provider for each candidate gap's incoming and outgoing leg, applying
  `fitServiceInGap` to find the earliest slot that satisfies *both* legs.
  A therapist is never returned as "available" at a time that would make
  the *next* booking's travel impossible — the deadline passed into
  `fitServiceInGap` already has the outgoing travel time subtracted.
- **`validateSlotStillAvailable`** re-runs this check inside the booking
  creation transaction (see `src/lib/booking/create-booking.ts`), plus one
  more raw overlap query immediately before insert — closing the race
  window between "the client saw this slot as open" and "the write
  actually happens" without holding a database transaction open across a
  travel-provider network call.
- **`src/lib/scheduling/recommend.ts`** — the Smart Booking Recommendation
  Engine (evaluates every therapist qualified for a service — has the
  `TherapistService` row, active, within their configured max travel
  radius — against the engine above, ranked by earliest availability).
  Never auto-assigns; always returns a ranked list for a human (or the
  client, for "any available therapist") to choose from.
- **`src/lib/travel/`** — the maps provider abstraction. Default
  (`MAPS_PROVIDER=none`/unset) is a Haversine-distance + fixed
  average-speed estimator, explicitly flagged `isEstimate: true` and
  documented as a development fallback, not a routed ETA. Set
  `MAPS_PROVIDER=google` and `GOOGLE_MAPS_API_KEY` for real
  traffic-aware routing via Google's Distance Matrix API; if that call
  fails for any reason, it falls back to the estimator rather than
  breaking dispatch.

## GPS privacy

Per the spec: clients must never see a therapist's exact coordinates —
only "your therapist is on the way, ETA 12 minutes." The single place this
is enforced is `src/lib/scheduling/public-availability.ts`'s
`toPublicAvailability()` mapper, which is the only code path between the
engine's real lat/lng-bearing internal types and anything served from
`/api/public/*`. It returns name, photo, rating, and a human "Today — 9:05
AM" label — nothing else. `tests/public-availability-privacy.test.ts`
asserts this holds for every code path (available now, available later,
unavailable), and it was additionally verified live by `grep`-ing the
actual JSON response from `/api/public/availability` for any
coordinate-shaped field.

Therapist location tracking itself (`Therapist.currentLat/currentLng`,
`TherapistLocationLog`) is scoped to active shifts: the location-update
endpoint (`/api/therapists/[id]/location`) refuses to record a ping for a
therapist whose status is `OFFLINE`, and the therapist PWA only requests
geolocation when tapping "Start Travel"/"Mark Arrived" — never a
background 24/7 watch. Admin/manager/dispatcher access to this data is
gated by the `therapists:gps:read` permission (accounting does not have
it, matching spec section 6).

## Security

- **Authentication**: JWT session in an httpOnly, `sameSite=lax` cookie
  (`secure` in production); passwords hashed with bcrypt (12 rounds).
- **Authorization**: every mutating/sensitive-read API route calls
  `requireSession()`/`requirePermission()` (or an explicit resource-owner
  check) before touching Prisma — see the "Architecture" note above on why
  `proxy.ts` deliberately isn't the security boundary for `/api/*`.
- **Input validation**: Zod schemas on every mutating route.
- **SQL injection**: Prisma's parameterized query builder throughout — no
  raw string-concatenated SQL anywhere in application code.
- **XSS**: no `dangerouslySetInnerHTML`, `eval`, or `Function()` usage
  anywhere in `src/` (verified by grep) — React's default escaping is the
  only rendering path.
- **Rate limiting**: an in-memory fixed-window limiter
  (`src/lib/rate-limit.ts`) on `/api/auth/login` (10 attempts/5 min/IP)
  and the public booking endpoints (30 availability checks/min,
  5 booking creations/10 min). Documented as single-instance-only in the
  module — a multi-instance production deployment should swap in a shared
  store (Redis/Upstash) behind the same function signature.
- **Financial data minimization**: booking amounts are stripped from API
  responses for roles that can see clients/bookings but lack `sales:read`
  (verified live against a dispatcher session).
- **Audit log**: every sensitive mutation (booking create/status change,
  service/therapist/client edits, settings changes, login) writes an
  `AuditLog` row via `src/lib/audit.ts`, viewable at `/audit-log`
  (super-admin/owner only).
- **Financial record immutability**: there is no DELETE route for
  bookings or payments at all — completed bookings are provably
  undeletable because the capability doesn't exist, matching spec section
  42's "use reversal/refund records instead." A `Refund` model exists in
  the schema for this; the refund-issuing UI is not yet built (see below).
- **Row Level Security**: not using Postgres RLS (this app uses a
  standalone PostgreSQL + Prisma, not Supabase) — equivalent protection is
  enforced at the application layer via the RBAC checks above. If migrating
  to Supabase for its managed Postgres/Auth/Realtime/Storage, RLS policies
  mirroring `src/lib/auth/permissions.ts` would be a natural addition,
  not a replacement for the app-layer checks.

## What's implemented vs. what's next

Everything described above is real, database-backed, and — where noted —
manually verified live, not just typechecked. Explicitly **not** built yet
(honest gaps, not hidden ones):

- **Reassigning a therapist on an already-assigned booking** — the booking
  detail page can advance a booking through its status lifecycle and
  cancel it, but there's no "change therapist" UI yet (would need the same
  re-validation `validateSlotStillAvailable` already provides).
- **Refund issuing UI** — the `Refund` model and `PaymentStatus` enum
  support it; the admin action to create one doesn't exist yet.
- **Receipt file uploads** for expenses (`Expense.receiptUrl` exists as a
  field; no upload endpoint or storage abstraction is wired in).
- **Real SMS/Email delivery** — `src/lib/notifications/` provider
  abstraction exists and is wired into the booking lifecycle (assignment,
  cancellation/no-show), but only the console fallback is implemented;
  wiring a real Twilio/Semaphore/Resend/SES account is a matter of adding
  one more `NotificationProvider` implementation.
- **Online payment gateway** — `src/lib/payments/` abstraction exists; only
  the manual/cash provider is implemented. Wiring PayMongo/Stripe means
  implementing `PaymentProvider.charge()` for that gateway.
- **Drag-and-drop calendar rescheduling** — the calendar renders a real
  day timeline per therapist, but moving a booking still goes through the
  booking detail page rather than a drag handle, specifically because spec
  section 40 requires the engine to re-validate before committing a drag,
  and a fake drag handle that doesn't do that would be worse than none.
- **Waitlist, client segmentation (VIP/at-risk/etc.), reviews UI, travel
  efficiency report, area analytics** — schema support exists for waitlist
  and reviews; the UI for these (spec sections 19, 18's segments, 26, 27)
  is not built. Per spec section 55/56 (MVP priority), these were
  deprioritized behind the scheduling engine, booking lifecycle, RBAC, and
  the therapist/client-facing apps.
